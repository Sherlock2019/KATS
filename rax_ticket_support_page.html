Ticket Support — where we are, and where we are going

For many years, RAX Core has carried our support operation. Every incident, every escalation, every customer conversation has passed through it. It has served this company faithfully, and the discipline it built into our teams is the reason we can raise the bar now. Thank you, Core.

But our customers' platforms have grown more complex, and their expectations have risen with them. Serving them better means evolving how we work — not simply logging tickets faster, but running a smarter, more efficient support process: one that captures the problem and not just the ticket, that turns every solved case into a compounding knowledge base the next engineer inherits, and that puts an AI agent alongside our people to help us see the unseen — the duplicate already open on another queue, the recurrence nobody linked, the pattern hidden across a year of tickets, the issue that was never a fault at all.

This is evolution, not replacement. KATS keeps what Core does well and adds what it was never built to do: the structure of a real problem analysis, and a memory that outlives the engineer who wrote it.

KT AI Enhanced Ticket Support System
1 Kepner-Tregoe problem analysis
  • Structured intake — WHAT, WHERE, WHEN, TREND and HOW MANY, instead of a free-text description
  • IS / IS NOT bounding — record what is affected and what is comparable but healthy; the cause must explain both
  • A/B distinction — put the broken case beside a working twin; the shortest list of differences is your candidate cause list
  • Single-variable testing — one reversible change, one target, so a result actually proves something
  • 5-Whys causal chain with evidence required at every link
  • Scale of impact — impacted nodes and VMs listed individually, healthy ones marked as the IS NOT set
2 AI agent — inference on every step
  • Automatic triage — runs the moment a ticket opens and answers four questions outright: is it already open elsewhere, have we seen it before, is it working as designed, is there a known fix
  • Duplicate & recurrence detection — matches on a normalized error signature and returns the other ticket's number, status, priority and age
  • "Works as designed" verdict — the answer that saves the most time is often stop, this is not a fault
  • 3 ranked probable causes — each with evidence for, evidence against, one single-variable test and an expected result
  • Plan review — critiques your hypotheses, removes what the evidence refutes, shortens the plan
  • Root-cause inference — proposes the cause, its coded category and a causal chain from the matched history
  • Drafts the handover from the tests you already ran, and the KB article from the solved ticket
  • Fleet health diagnostic — scores the estate and ranks what to fix first
  • Time saved, quantified — every plan is costed against what the issue took the first time
  • It proposes, you decide — nothing changes ticket state on its own, and every claim shows its evidence
3 Smart Knowledge Base — memory that compounds
  • One schema for every article — so a retrieval agent can actually search it
  • Error-signature normalization — strips timestamps, UUIDs, request IDs and host IPs while keeping meaningful constants, so the same fault matches twice
  • Explainable search — every hit shows a match score and why it matched
  • Automatic de-duplication — republishing the same fault bumps its reuse count instead of creating a near-twin
  • Secret scrubbing — passwords, keys, tokens, SSH targets and emails are detected and redacted before publishing; publishing is blocked if you switch it off
  • Verified-fix gating — an unverified article never outranks a proven one
  • Reuse tracking — the KB learns which articles actually get used, not just which rank well
  • Vector-search ready — every article carries an assembled embedding field and exports as JSON
4 Problem & recurrence management
  • Problem records outlive the ticket and own the root cause — incidents merely reference them
  • Recurrence counting — the evidence that funds a permanent fix
  • Known Error state — a verified workaround with no permanent fix yet, expressed properly
  • Blast radius and cost — every affected customer, and the hours spent across all linked cases
  • Auto-clustering — unlinked cases sharing a signature are proposed as one Problem
  • Coded root-cause taxonomy — so "what breaks us most often" becomes a chart, not an opinion
5 Customer & fleet intelligence
  • Customer topology mind map — pick a customer and every open ticket is drawn as a mermaid mind map, customer → site → infra location → issue, with the hotspot location called out and the ticket you are typing already on the map
  • Ticket history per customer — last 3 days / week / month or any custom date range, with per-day intake, MTTR against SLA, breakdowns by component, site and root cause, and CSV export
  • Customer 360 — full case history, MTTR trend, recurring issues, open Problems, top failing components
  • Related cases — same signature, same Problem, same customer+component, same customer
  • Case timeline — the event stream, exportable as the handover artefact
  • Operations dashboard — 1 day / 3 days / 1 week / 30 days, opened vs solved, pending, P1s, MTTR
  • Top 10 customers, issue types and infrastructure by volume, with open counts highlighted
  • Infrastructure health score with the factors costing points and a prioritised remediation plan
6 Built for the way engineers work
  • Colour-coded ownership — red sections are customer input, blue are support input
  • KB-readiness meter — shows live what is still missing before the ticket can teach the next one
  • Comments on every step, not just one thread at the bottom
  • Autosave and draft restore, and full ticket export as JSON
